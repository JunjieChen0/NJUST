# ADR-006: 性能预算与 Bundle Size 红线

## Status

Accepted

## Context

需要将构建体积门禁、激活性能目标和实际测量分开，避免把历史体积或没有样本的遥测报告当作当前性能结论。旧评审中的体积比例和优化幅度不再作为本页基线。

## Decision

| 项目                    | 预算或目标 | 执行边界                                            |
| ----------------------- | ---------- | --------------------------------------------------- |
| `src/dist/extension.js` | 30 MiB     | `scripts/check-bundle-size.mjs` 检查，超限退出失败  |
| 扩展激活 P95            | 500 ms     | 性能目标，须提供真实样本，不是当前 Code QA 独立门禁 |
| 扩展激活 P99            | 1500 ms    | 性能目标，须提供真实样本                            |
| dist 总体积             | 120 MB     | 设计预算，脚本会报告体积，但不单独以此阈值拦截      |

体积检查从仓库根目录运行：

```sh
pnpm bundle
pnpm check:bundle-size
```

激活测量使用 `scripts/report-activation-perf.mjs`，需显式指定真实遥测目录。没有样本时不作达标判断；冷启动和热启动应分别说明。

源码构建与已打包 VSIX 的激活测试分开执行。清单、资源和命令注册变更必须检查实际安装包，保存包哈希，不能只凭开发态测试通过发布。

## Consequences

- 体积增长可由 CI 阻止；依赖和资源变化需要解释来源。
- 性能目标需要采样方法、环境、时间范围及样本数支持，不能从一次成功激活推断分位数。
- SDK 动态加载、数据外置或构建插件优化须单独评估启动延迟、资源分发和兼容性，不沿用旧版本的收益估算。
- 更新硬门槛时，应同时修改脚本、工作流及对应文档，并保留可复核的理由。
